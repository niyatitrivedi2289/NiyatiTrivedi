Overview

Two portals. One confused developer.

Worldpay had two separate developer portals — one for Merchant APIs, one for Partner APIs. Developers needing both had to navigate two different systems, two sets of credentials, and two sets of documentation. This caused friction, confusion, and avoidable support load.

The goal was to merge both into a single, coherent developer experience — one that could scale with the business after the FIS acquisition.

Goals

Two perspectives. One shared outcome.

01

Developer goal

Make it fast and obvious to find the right API, understand how to use it, and start building — without switching between portals or asking for help.

02

Business goal

Create a single platform that reduces integration time, lowers support overhead, and positions FIS as a modern developer-first payments company post-acquisition.

Challenges

The problems we had to solve.

🗂️

Fragmented information architecture

Merchant and Partner docs lived in completely different systems. No shared navigation, no cross-linking, no unified search.

🔑

Duplicate authentication

Developers needed separate credentials for each portal. Two login flows, two dashboards, double the cognitive overhead.

🏗️

Legacy technical constraints

Existing portals had different tech stacks, different CMS systems, and different release cadences — merging them meant navigating real infrastructure limits.

👥

Multiple stakeholder groups

Merchants, integration partners, and internal engineering teams all had different needs and expectations from the same platform.

📉

Poor discoverability

Developers couldn't easily find relevant APIs or understand the relationship between products. Search was broken. Taxonomy was inconsistent.

🔄

Post-acquisition alignment

After FIS acquired Worldpay, brand guidelines, content ownership, and product naming all needed to be reconciled across teams.

Key insight

Every leading competitor had already solved unification. The baseline expectation for developers was a single portal, instant sandbox access, and interactive documentation. We were behind on all four. This wasn't a design opportunity — it was a competitive necessity.

Design Approach

Start with structure. Then add clarity.

We approached the design in three phases — information architecture first, then interaction patterns, then visual language. We deliberately separated these to avoid the trap of making things look good before they worked well.

1

Unify the IA

Map every content type across both portals. Define a single taxonomy. Remove duplication. Create a hierarchy that made sense to a developer, not an internal product team.

2

Simplify the flows

Reduce the number of steps to reach a working API key. Unify authentication. Design a single onboarding flow that branched by persona — not by portal.

3

Build for scale

Design a component system and content model that engineering and DevRel could maintain. The platform needed to grow without becoming messy again.

Usability Testing

Three rounds. Real developers. Real findings.

We ran three rounds of moderated usability testing — one per major design iteration. Participants ranged from junior developers new to payment APIs to senior engineers with 10+ years of integration experience.

1

Round 1 — Navigation

8 participants · Prototype testing

  • Users couldn't distinguish Merchant vs Partner APIs without explanation
  • Search was the most-used feature, but returned poor results
  • Top nav labels were unclear — "Resources" meant nothing
2

Round 2 — Onboarding

6 participants · Mid-fidelity

  • Stepped onboarding reduced confusion by 60% vs baseline
  • Test key flow was still too long — reduced to 3 steps
  • Developers wanted code examples immediately, not after setup
3

Round 3 — Full flow

7 participants · High-fidelity

  • All users completed the core task within 8 minutes
  • SUS score improved from 52 to 74 (industry average: 68)
  • Remaining issues: mobile doc experience, error state copy

Key Design Decisions

Six choices that shaped the platform.

01
Use-case taxonomy instead of product taxonomy

Internal product names (Merchant API, Partner API) had no meaning to external developers. Use-case labels (Payments, Payouts, Identity) matched how developers thought about their integration needs.

Navigation task completion improved significantly in Round 2 testing. Developers found the right API without asking for help in 7 of 8 sessions.

02
Unified authentication with a single API key dashboard

Two login systems for one company was a basic trust failure. Merging auth eliminated the most-cited friction point from research.

Support tickets related to authentication dropped after launch. Developers could manage all credentials from one dashboard.

03
Code-first documentation layout

Observation showed developers scanned for code before reading prose. Leading with a working example on every API page aligned with actual reading behaviour.

Time-to-first-API-call reduced. Users reported higher confidence during testing — the code gave them a concrete starting point.

04
Keyboard-first global search (⌘K)

Developers prefer keyboards. A persistent command palette felt native to their workflow and removed reliance on navigation menus.

Search became the most-used navigation method post-launch. Users found it faster than sidebar navigation for all doc-retrieval tasks.

05
Component-based content model for scale

The old portals had bespoke layouts for everything. As the product grew post-acquisition, we needed a system teams could build on without a designer in the room.

Engineering velocity for new API pages increased. DevRel could publish documentation updates without custom design work for each release.

06
Dark and light mode, built on accessible contrast

The earlier site was light-only and had several accessibility issues: low-contrast grey body text, brand green and yellow failing WCAG AA on white, and unclear focus states. Developers also asked for a dark theme to match their IDEs.

A token-based theme with a persistent toggle. Brand accents are tuned per theme to pass AA, code blocks stay dark in both modes, and the preference carries across every page.

Solution

One platform. Five core experiences.

🏠

Unified home

A single entry point with role-based onboarding paths. Developers self-selected their use case and landed in the right place immediately — no portal choice required.

📚

Integrated documentation

All API references, guides, and changelogs under one information architecture. Shared navigation, shared search, consistent page templates across every product.

⚡

Instant sandbox

Self-serve test key provisioning in under 60 seconds. Developers could start building without waiting for manual approval or switching tools.

🔑

Single credentials dashboard

One place to manage all API keys, webhook configurations, and team access. Eliminated the need for separate logins across merchant and partner products.

🧪

Try it — no login required My design

Every endpoint in the API reference has a live "Try it" console pre-filled with sandbox credentials and a working request body. Developers can send a real call and inspect the response before creating an account, so evaluation starts on the first visit instead of after sign-up.

Today the live site keeps Try it behind a login — the console exists, but evaluation now starts after sign-in.

Since I led the design, Worldpay has gone through a merger with FIS and a later separation into its own company. Reflection — 2026 Perspective

What I'd do differently now.

Looking back from 2026, with more experience in platform and systems design, there are things I'd change — and things I'm still proud of.

What I learned

Platform design is as much organisational as it is UX. The hardest problems weren't layout or interaction — they were content ownership, naming conventions, and getting six stakeholder teams to agree on a taxonomy.

Research matters more when the audience is technical. Developers gave precise, honest feedback. The focus groups were some of the most useful sessions I've run — because the participants could articulate exactly what was broken.

What I'd improve today

Earlier content strategy. We started with navigation before we had a content model. In hindsight, defining the content types and ownership model first would have saved weeks of rework.

More quantitative measurement. The directional metrics we tracked were useful, but I'd now instrument the platform for funnel analytics from day one — so design decisions could be validated with data, not just usability sessions.

Design systems sooner. We built components reactively. Starting with a token-based design system would have accelerated consistency across the multi-team environment.
